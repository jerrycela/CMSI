## 1. UX 問題清單（按嚴重度排序）

### 嚴重度：高（會讓使用者困惑或無從行動）

---

**問題 H1：「Token」這個詞對非工程師毫無感覺**

現況：Dashboard 到處出現「5,600 tokens」、「估計 Token：N」、「整體自動載入超過 40,000 tokens」。

問題：Token 對工程師來說是熟悉的單位，但對非工程師使用者而言，「tokens」和「credits」、「字」的區別完全不直覺。更根本的問題是：「5,600 tokens 到底是多還是少？」使用者沒有參照基準，數字本身沒有意義。

---

**問題 H2：概覽 Tab 缺乏「現在怎麼了」的即時判斷**

現況：概覽 Tab 規劃顯示 token 總量 + 資料新鮮度 + 關鍵警告 + sections 排行。

問題：這四件事放在一起，使用者打開 Dashboard 的第一眼，不知道「現在狀態是好是壞」。計畫裡有 8,000 tokens 的警戒線，但 Dashboard 預計用 tooltip 揭示，使用者要滑鼠移過去才看得到。健康狀態應該主動告訴使用者，而不是藏在 tooltip 裡等使用者去挖。

---

**問題 H3：路徑是工程師語言，「複製路徑」對非工程師不直覺**

現況：顯示完整絕對路徑 `/Users/admin/openclaw/CLAUDE.md`，提供「複製路徑」按鈕，附說明「Finder 中按 Cmd+Shift+G，貼上路徑即可前往」。

問題：Round 5 已注意到這個問題並提供了 Finder 說明，但「複製路徑 → 打開 Finder → 按快捷鍵 → 貼上」這個流程對非工程師仍然有摩擦。更關鍵的是：使用者在 Dashboard 上看到一個路徑，他真正想做的事是「打開這個資料夾」，而不是「複製這串文字」。動作名稱應對應使用者的意圖，而不是技術操作。

---

**問題 H4：Skills 的 68 個項目沒有快速定位方式**

現況：Skills 拆成兩個 Tab（手動 25 個、Plugin 43 個），無搜尋或篩選功能（v2 範圍）。

問題：68 個項目中，使用者常常是「我記得有一個關於 Vue 的 Skill，但不確定叫什麼」，在沒有搜尋的情況下需要逐頁掃描。對於 68 個項目，純粹的捲動瀏覽效率很低。至少需要字母順序排列 + 關鍵字篩選，這不是 v2 功能，而是 v1 的基本可用性要求。

---

### 嚴重度：中（體驗不佳但可以用）

---

**問題 M1：兩個 Skills Tab 的分法邏輯不符合使用者心智模型**

現況：Skills 按安裝來源分成「手動」和「Plugin」兩個 Tab。

問題：使用者找 Skill 時通常是「我要找跟 Vue 有關的 Skill」，不是「我要找手動安裝的 Skill」。按安裝來源分類是技術邏輯，不是使用者的認知邏輯。從使用頻率來看，兩個 Tab 都標「偶爾」，但把同一類東西（Skills）拆成兩頁反而讓兩頁都更難用。

---

**問題 M2：Docs Tab 的定位不清楚**

現況：Docs Tab 只顯示 `~/.claude/docs/` 的 metadata，不顯示內容。

問題：使用者打開 Docs Tab，看到的是一堆檔名和數字（agents.md：298 tokens，git-workflow.md：N tokens），但不知道「這些文件是幹什麼的，我什麼時候會用到它們」。如果不顯示內容，至少應顯示每個文件的一句話摘要，否則這個 Tab 傳遞的唯一資訊是「你有幾個 docs 文件，它們分別多大」，使用價值極低。

---

**問題 M3：tokenBudget 的 null 狀態處理體驗很差**

現況：初次掃描時 tokenBudget 全為 null，計畫說明「顯示 null」，行動指引是「執行 /context 後手動更新」。

問題：使用者打開 Dashboard，看到一個 token 預算表格全部寫著「null」，會以為是程式出錯，而不是「這需要我自己填」。null 狀態需要主動說明：「這些數字需要您在 Claude Code 裡跑 /context 後手動填入」，並且提供步驟說明，不能只顯示 null 讓使用者自己猜。

---

**問題 M4：資料新鮮度的位置和重要性不匹配**

現況：頁首顯示「掃描於 X 分鐘前」。

問題：如果資料是 3 天前的，使用者看到的所有數字都是過時的，應該最優先告知。但「頁首」通常是使用者掃過去就跳過的地方（就像網頁的 header 一樣）。資料太舊時，應該用更醒目的方式提示（例如橫幅警告），而不是靜靜躺在 header 的某個角落。

---

**問題 M5：CLAUDE.md 展開/收合的預設狀態設計**

現況：預設顯示前 300 字，提供「展開全部」按鈕。

問題：300 字對全域 CLAUDE.md（597 字）來說只是一半，顯示一半的內容有點尷尬——夠多了讓使用者以為看完了，但又沒有完整。更好的做法是：預設顯示前 100 字（足夠判斷這是什麼內容），明確標示「顯示部分，共 N 字」，讓使用者有意識地選擇要不要展開。

---

### 嚴重度：低（優化項目，不影響核心功能）

---

**問題 L1：sections 排行的呈現方式**

現況：計畫說「sections 排行前 3」，顯示在概覽 Tab。

問題：沒有說明這三個項目是以什麼形式呈現（數字？圖表？列表？）。只有前 3 名有名次感，最好用明確的排名視覺（1st、2nd、3rd 標示）搭配實際數字，讓使用者一眼看出哪個 section 最「重」。

---

**問題 L2：技術術語出現在 UI 裡**

現況：data.json 結構中有 `type: "symlink"` 欄位，計畫說「含型態標示（symlink/目錄/檔案）」要在 Skills Tab 顯示。

問題：symlink 是技術詞。使用者看到「類型：symlink」不知道這意味著什麼。如果一定要顯示，至少改成更白話的說法，或完全不顯示（使用者不需要知道實作細節）。

---

**問題 L3：「更新」指令的呈現方式**

現況：計畫說顯示「更新：cd dashboard && npm run scan」。

問題：這是給工程師看的指令。非工程師使用者看到這串文字，需要打開 Terminal，知道 cd 是什麼、知道 && 是什麼。如果這個工具的對象包含非工程師使用者，指令說明要更友善，至少改成「在終端機裡貼上以下指令」，並提供一個複製按鈕。

## 2. 具體改善建議（Before / After 對比）

### 改善 1：Token 換成有感的單位

**Before：**
```
全域 CLAUDE.md：5,600 tokens
整體自動載入：38,000 tokens
警戒線：40,000 tokens
```

**After：**
```
全域指令檔：5,600 字（約佔每次對話額度的 14%）
目前已用額度：38,000 / 40,000（95%，接近上限）
[紅色進度條，填滿 95%]
```

說明：把「tokens」改成「字」（大多數人理解「字數」），加上百分比和進度條讓「多不多」立刻有感，不用使用者自己換算 38000 佔 40000 的幾成。

---

### 改善 2：健康狀態標誌放在最顯眼的位置

**Before：**
概覽 Tab 顯示四個區塊（token 總量、資料新鮮度、警告、sections 排行），使用者自己判斷狀態好壞。

**After：**
```
[大字] 現在狀態：正常 / 注意 / 警告
[顏色：綠 / 黃 / 紅]

正常：所有數字在合理範圍
注意：全域指令檔超過 6,000 字，或資料超過 24 小時未更新
警告：總用量超過 40,000 字（80% 以上），或某個專案 CLAUDE.md 超過全域大小
```

說明：給一個整體健康狀態判斷，使用者打開 Dashboard 0.5 秒就知道「現在是不是有問題」，不需要自己看數字再判斷。

---

### 改善 3：「複製路徑」改為「前往資料夾」

**Before：**
按鈕文字「複製路徑」，旁邊說明文字「Finder 中按 Cmd+Shift+G，貼上路徑即可前往」。

**After：**
按鈕文字「前往資料夾」，點擊後：
1. 自動複製父目錄路徑到剪貼簿
2. 出現提示框：「路徑已複製！在 Finder 選單列點「前往 > 前往檔案夾」，貼上即可。」
   配上一張 3 秒就能讀懂的步驟圖（或截圖）

說明：按鈕名稱對應使用者意圖（前往資料夾），而不是技術操作（複製路徑）。提示框在需要時才出現，不佔版面。

---

### 改善 4：Skills 合併成單一 Tab，加上即時篩選

**Before：**
「Skills（手動）」Tab 和「Skills（Plugin）」Tab，各自獨立，無搜尋功能。

**After：**
單一「Skills」Tab：
- 頁面頂部：篩選框（即時過濾，不需要 submit）
- 來源可用小標籤區分（手動安裝 / Plugin），但所有 Skills 在同一個列表
- 每個 Skill 卡片顯示：名稱、一句話摘要、大小（字數）、來源標籤
- Plugin Skills 可以用 pluginName 作為分組標題，在同一頁面裡摺疊

說明：篩選是比分頁更靈活的分類方式，68 個項目的清單加一個即時篩選框，比在兩個 Tab 之間切換更實用。

---

### 改善 5：Docs Tab 加上一句話摘要

**Before：**
Docs Tab 顯示：`agents.md | 298 tokens | 2,233 bytes`

**After：**
Docs Tab 顯示：
```
agents.md
用途：說明如何建立和管理 Agent 團隊（多工協作）
大小：298 字 | 最後更新：1 月 15 日
```

說明：scan.js 已讀取完整內容，取第一段或前 100 字作為摘要不需要額外工作，但使用者的理解成本大幅降低。

---

### 改善 6：null 狀態改為明確引導

**Before：**
token 預算表格中，所有欄位顯示 null。

**After：**
```
[灰色虛線方框]
Token 預算明細尚未設定

這些數字需要您手動取得並填入：
1. 在 Claude Code 終端機輸入 /context
2. 找到 token budget 相關數字
3. 開啟 public/data.json，填入 tokenBudget 區塊

[複製說明] 按鈕（複製填寫說明文字）
```

說明：把 null 換成空狀態設計（empty state），讓使用者知道這不是錯誤，而是需要一個主動步驟。

---

### 改善 7：symlink 改為不顯示或換詞

**Before：**
Skills 清單顯示「類型：symlink」

**After：**
完全不顯示類型欄位（使用者不需要知道）。
或，如果基於技術原因必須顯示，改為「捷徑安裝」（對 symlink 的白話解釋）。

## 4. 「第一個畫面」具體設計描述（文字線框）

打開 Dashboard，畫面分三個層次：

**第一層（最上方，整個視窗的 20%）**
一個大色塊，顏色代表健康狀態（綠/黃/紅）。左側大字「現在狀態：正常」，右側小字「掃描於 3 分鐘前」。如果超過 24 小時，這個色塊會加一行橫幅警告「資料已過時，建議重新掃描」。

**第二層（中間，整個視窗的 50%）**
三個並排的數字卡片：
- 卡片 1：「全域指令檔」+ 大數字（字數）+ 佔對話額度的百分比
- 卡片 2：「Skills 總數」+ 大數字（68）+ 手動/Plugin 分佈
- 卡片 3：「專案設定」+ 大數字（找到幾個 CLAUDE.md）+ 最大那個是哪個

**第三層（下方，整個視窗的 30%）**
最重的三個 Sections 排行，格式：「第 1 名：Skill 路由表，1,200 字，佔全域指令檔 21%」。每個項目旁邊有 tooltip（滑鼠移上去顯示行動建議）。

Tab 列固定在畫面上方（非捲動消失型），點擊切換。

## 5. 本輪 Insight

### Insight 1：「讓使用者自己判斷」是設計者偷懶的表現

Round 5 的 Dashboard 設計提供了所有數字，並透過 tooltip 揭示「看到這個數字要做什麼」。這個設計的隱性假設是：使用者願意主動去探索 tooltip，並且有能力從數字自己判斷狀態好壞。

但好的 Dashboard 設計的核心是**代替使用者做判斷**，然後把結論告訴使用者。Google 分析、健康 App、汽車儀表板——都先給你一個「現在好不好」的整體狀態，再讓你往下看細節。Dashboard 不應該是一個讓使用者自己分析數字的工具，而是一個已經分析好、等著告訴你結論的工具。

### Insight 2：Tab 的分類邏輯應對應「使用者的問題」，而非「資料的來源」

Round 5 把 Skills 依安裝方式分成兩個 Tab，是因為資料結構上有 manual/plugin 的區分。但使用者的問題不是「我手動安裝了哪些？」，而是「我現在有哪些 Skills？」。

資料結構和 UI 結構是兩件事。資料可以有 source 欄位，但 UI 不必照著資料結構分 Tab。使用者的問題應該是 Tab 分類的依據，不是資料的分類方式。

### Insight 3：空狀態（Empty State）是 UX 設計最容易被忽略的場景

計畫裡最薄弱的 UX 場景是「第一次打開 Dashboard，tokenBudget 全是 null」。這個場景使用者一定會遇到，但計畫的處理方式是「顯示 null」。

空狀態設計（empty state design）是 UX 的基本功：當資料缺失時，不能只顯示空白或 null，而要主動告訴使用者「為什麼這裡是空的」和「要做什麼才能填滿它」。這個 insight 也適用於 Docs Tab（如果 docs/ 目錄為空）和 allProjects（如果掃描結果為零）。

### Insight 4：第一個畫面的 30 秒體驗決定了工具是否會被持續使用

專案目標是「在 30 秒內看到自己電腦上所有 CLAUDE.md 的狀況」。30 秒是個很好的設計約束，但 Round 5 的計畫更多在考慮「資訊是否完整」，較少考慮「使用者在 30 秒內的視線路徑」。

一個人打開 Dashboard，視線會先落在哪裡？數字最大的地方。顏色最突出的地方。第一個看到的文字。Round 6 的設計建議把這個視線路徑明確化：健康狀態 → 三個關鍵數字 → 需要注意的細節。這個路徑設計確保使用者在 30 秒內能完成第一個目標，不需要四處找資訊。

## 6. 與 Round 5 的差異總結

| 面向 | Round 5 的決定 | Round 6 的建議 | 差異性質 |
|------|--------------|--------------|---------|
| Token 單位 | 顯示 tokens 數字 | 改為「字」+ 百分比 + 進度條 | 語言友善度 |
| 健康狀態 | 使用者看數字自己判斷 | 系統先判斷，給整體燈號 | 設計哲學 |
| 路徑操作 | 「複製路徑」按鈕 | 改為「前往資料夾」，點後出現引導提��� | 使用者意圖對應 |
| Skills Tab 數量 | 2 個 Tab（手動/Plugin） | 1 個 Tab（合併），加即時篩選 | 資訊架構 |
| Skills 瀏覽 | 無搜尋（v2 範圍） | 即時篩選為 v1 基本需求 | 優先級調整 |
| Docs Tab | 只有 metadata | 加一句話摘要 | 最小有意義內容 |
| Tab 名稱 | CLAUDE.md 普查、Docs | 指令設定、參考文件 | 語言友善度 |
| tokenBudget null | 顯示 null | 空狀態設計（說明 + 步驟引導）| 空狀態處理 |
| 資料過時警告 | 頁首靜態文字 | 橫幅警告（醒目）+ 條件觸發 | 重要性對應視覺權重 |
| CLAUDE.md 預覽 | 前 300 字預設展開 | 前 100 字 + 明確「僅顯示部分」 | 降低誤解 |
| symlink 顯示 | UI 裡顯示 symlink 型態 | 不顯示或換白話詞 | 技術術語清理 |
| 更新指令顯示 | 直接顯示 shell 指令 | 白話說明 + 複製按鈕 | 非工程師友善度 |
| 第一屏設計 | 未明確描述視線路徑 | 三層結構，明確視線路徑設計 | 第一印象設計 |

### 哪些 Round 5 決定 Round 6 維持不動

- 技術架構（Vue 3、scan.js、data.json）：無異議，完全沿用
- Tab 結構基本方向（概覽為預設、4-5 個 Tab）：方向正確，只調整數量和命名
- 內容展開/收合概念：機制正確，只調整預設顯示字數
- tooltip 作為行動指引的載體：適合補充性說明，保留

### 實作優先級建議（給 Phase 3 前端開發者）

Phase 3 實作時，按以下順序處理 UX：

1. 健康狀態燈號（最重要，影響第一印象）
2. 數字 + 百分比 + 進度條（替換純 token 數字）
3. Skills 合併 + 即時篩選（避免兩個 Tab 各自沒用）

5. Tab 名稱改為白話
6. 路徑操作按鈕改名
7. 移除 symlink 標示

以上 7 點均在 v1 範圍內，不新增任何掃描邏輯或資料結構，只影響 Vue 元件的呈現層。
