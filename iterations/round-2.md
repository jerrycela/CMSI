# Round 2 — 計畫審查報告

審查日期：2026-02-19
審查角色：計畫審查員（Sonnet 4.6）
審查對象：第 1 輪優化後的 CMSI Dashboard 計畫

---

## 審查前言

本次審查的對象是：原始 6 階段計畫（Express + monorepo 全棧架構），經過 20 點優化後的精簡版本，以及 Phase 1 Discovery 的實際調查成果。

審查策略：**從實際的發現資料反向檢驗計畫的假設是否成立**，不只是評估計畫本身的邏輯。

---

## 一、整體評價

**評分：7 / 10**

優化後的計畫方向正確，從過度工程化（Express + monorepo + WebSocket）收斂到合適規模（Node 腳本 + 單一 Vite 專案 + JSON）。Phase 1 Discovery 的品質也相當高，實際探測了工具的限制並記錄了 3 個關鍵發現。

扣分的原因：**計畫的成果定義依然模糊**，特別是「使用者能用這個 Dashboard 做什麼決策」這個核心問題沒有被回答。簡化了技術棧，但沒有同步簡化功能目標的期望，導致 MVP 範圍仍然偏大。

---

## 二、優點分析

### 2-1. 技術選型的簡化是正確的

原始計畫的 Express + monorepo 對這個工具來說是嚴重過度工程化。這個 Dashboard 的使用者只有一個人（開發者本人），資料是靜態的（每天 cron 更新一次），不需要任何後端 API 層。

優化後的「Node 腳本產生 data.json → Vite 讀取」架構，準確抓住了這個場景的本質：**這是一個個人工具，不是一個服務**。這個判斷很成熟。

### 2-2. Phase 1 Discovery 的三個發現都是高價值的

- `toolUses.input` 永遠是 null 這個發現，避免了後續開發浪費在一個死路上
- auto-analyze 腳本有重複計數 bug，這表示任何直接信任腳本輸出的功能都需要自行去重
- `~/.claude/` 不是 git 倉庫，澄清了變更追蹤的方式只能靠備份快照

這三個發現的品質都很高，都是在實際動手之前必須知道的事。

### 2-3. MVP 功能範圍縮減（Token 分析 + Skills 管理）方向對

四大功能中，Token 分析和 Skills 管理是資料來源最清晰的兩個：
- Token 分析：直接讀 `~/.claude/` 目錄的檔案計算字數，沒有任何外部依賴
- Skills 管理：掃描 `~/.claude/skills/` 和 `~/.agents/skills/` 目錄，資料完全本地

把規則使用頻率（需要解析大量 JSONL）和優化歷史追蹤（需要備份 diff 邏輯）留到第二階段，是合理的優先順序。

### 2-4. 「一個指令搞定」的設計思路對

`npm run dashboard` 一個指令：執行 Node 腳本更新 data.json → 啟動 Vite 開發伺服器 → 打開瀏覽器。這種設計把使用摩擦降到最低，符合這個工具的定位（不是每天都需要用，但用的時候要快速）。

### 2-5. 備份比對策略務實

接受「~/.claude/ 不是 git 倉庫」這個現實，改用備份快照比對，是典型的「務實優於教條」。不強求做 git init，而是利用現有的 11 個備份點，這個決定很對。

## 三、缺點與風險分析

### 3-1. 核心問題：Dashboard 要讓使用者做出什麼決策？（最大缺點）

整個計畫從頭到尾都在討論「顯示什麼資料」，但沒有討論「使用者看完資料後要做什麼」。

舉例說明：Token 分析顯示 CLAUDE.md 是 5.6k tokens，這個數字代表什麼意思？使用者要採取什麼行動？什麼情況下應該刪內容、什麼情況下保留？計畫沒有回答這些問題，Dashboard 很可能變成一個「很漂亮但沒人看」的面板。

這是設計層面的根本缺失，不是技術問題。

### 3-2. JSONL 解析的工作量被低估

Phase 1 Discovery 確認需要直接解析 JSONL 才能取得 Read 工具的 file_path。但計畫對 JSONL 解析的複雜度估計不足：

- JSONL 檔案可能很大（findings.md 提到 fileSizeBytes: 284067，約 280KB 一個 session）
- 「只看最近 30 天」的限制實作起來需要先掃描所有 session 的日期
- 重複計數 bug 需要在解析層處理去重邏輯
- 不同 project-key 的資料夾命名規則需要先探索

優化項目 11（「JSONL 只看最近 30 天，串流處理」）只有一句話，但這背後的工作量可能是整個資料腳本中最複雜的部分。

### 3-3. 「所有 CLAUDE.md 路徑」功能和其他功能的關係不清楚

使用者額外需求是「能檢視電腦上所有專案的 CLAUDE.md 內容」。這個需求和原始四大功能（Token 分析、規則頻率、優化歷史、Skills 管理）之間的關係沒有被明確定義：

- Token 分析是分析全域 CLAUDE.md，還是所有專案的 CLAUDE.md 加總？
- Skills 管理的 Skills 使用頻率是全專案合計，還是各專案分開顯示？
- 掃描所有專案的 CLAUDE.md 需要遍歷整個檔案系統，要掃哪些目錄？深度多少？

這些問題在計畫中沒有答案，實作時可能需要返工。

### 3-4. data.json 的設計沒有具體定義

計畫說「一個腳本掃所有資料，產出一個 data.json」，但這個 JSON 的結構沒有被設計出來。資料結構的設計其實是整個專案中最重要的一步，因為它決定了：

- 腳本要收集什麼資料
- Vue 前端要如何渲染
- 哪些計算在腳本端做，哪些在前端做

沒有 data.json 的結構定義，Phase 2 的腳本開發和 Phase 3 的前端開發會缺乏共同契約，容易在整合時出問題。

### 3-5. 跳過 ESLint + Prettier 的代價

優化項目 16 說「v1 先跳過 ESLint + Prettier」。在個人工具上這通常沒問題，但這個專案計畫有 6 個開發階段，如果 v1 之後有 v2，沒有統一格式的程式碼在後期維護時會增加摩擦。

更大的問題是：「v1 先跳過」這個決定沒有配套的「v2 加回來」計畫，很可能永遠跳過。

## 四、矛盾檢查

### 矛盾 1：「不需要後端伺服器」vs「需要讀取本地 JSONL 檔案」

使用者額外需求說「不需要後端伺服器」，但 Vue 前端（在瀏覽器中運行）無法直接存取本地的 JSONL 檔案。解決方案是「Node 腳本預先產生 data.json」，但這個解決方案只在腳本執行時生效。如果使用者想要看「最新資料」，他需要手動再跑一次腳本。

計畫的架構能解決這個矛盾，但沒有明確說明「資料新鮮度」的使用者體驗：使用者需要知道「這份資料是什麼時候產生的」，以及「如何更新它」。

### 矛盾 2：「簡化到 3 個開發階段」vs task_plan.md 仍維持 6 個階段

優化項目 15 說「壓縮成 3 個開發階段」，但實際的 `task_plan.md` 仍然是 6 個階段，而且各階段的 checklist 沒有更新來反映優化後的決策（例如 Phase 2 還在說「設定 Express + TypeScript 後端」和「建立 monorepo 結構」，這些已經被砍掉了）。

計畫文件和實際決策之間出現了漂移，task_plan.md 已經是過時的文件。

### 矛盾 3：「規則使用頻率用簡單排名表，不用熱力圖」vs 功能實際依賴 JSONL 解析

優化項目 20 說把熱力圖改成排名表（好決定），但這個功能的資料來源是 JSONL 解析，而 JSONL 解析被歸類為「第二階段」。優化項目 6 說「MVP 先做 Token 分析 + Skills 管理」。

所以規則使用頻率到底是 MVP 的一部分，還是第二階段？這個邊界不清楚。

## 五、遺漏檢查

### 遺漏 1：data.json 的更新策略

腳本產生 data.json 之後，這個檔案要放哪裡？是放在 Vite 的 `public/` 目錄（靜態資源）？還是 `src/assets/`？還是專案根目錄？這決定了 Vite 開發伺服器能不能直接讀到它。

### 遺漏 2：全專案 CLAUDE.md 掃描的邊界條件

���掃描電腦上所有 CLAUDE.md」這個功能需要定義：
- 從哪個根目錄開始掃（`/Users/admin/` 還是 `/Users/admin/Documents/` 還是 `~/`）？
- 排除哪些目錄（`node_modules/`、`.git/`、系統目錄）？
- 深度限制是多少？

沒有這些邊界條件，掃描腳本可能跑幾分鐘，或者掃到不相干的地方。

### 遺漏 3：資料腳本的執行環境要求

腳本需要 Node.js，但沒有說明需要哪個版本。如果使用 ESM（`import` 語法）還需要設定 `package.json` 的 `"type": "module"`。這些看起來小的細節，在第一次執行時容易卡住。

### 遺漏 4：Skills 的「使用頻率」資料來源

Skills 管理要顯示使用頻率，但「哪個 skill 被用了多少次」這個資料在哪裡？CLAUDE.md 中有 Skill 路由表，但實際的 skill 調用記錄需要從 JSONL 中解析 `Skill` 工具的調用，這和 JSONL 解析的複雜度問題又連在一起了。

如果 Skills 管理 MVP 版只顯示「已安裝哪些 skills」和「每個 skill 的大小」，而不是使用頻率，這個問題就消失了。但計畫沒有明確說清楚。

### 遺漏 5：rules/ 目錄的異常未被列為行動項目

findings.md 發現「rules/ 目錄的舊檔案可能仍在被自動載入，佔用不必要的 token」，但這個發現只是被記錄下來，沒有成為任何階段的行動項目。如果這是真的，Dashboard 顯示的 Token 分析就會有誤差，因為 rules/ 的 token 也被計入了。

## 六、Insight

### Insight 1：這個計畫的真正價值在「發現」，不在「Dashboard」

Phase 1 Discovery 最有價值的產出不是計畫本身，而是那三個具體發現（claude-log 的限制、auto-analyze 的 bug、不是 git 倉庫）。這些發現本身就已經讓使用者對自己的工具基礎設施有了更清楚的認識。

這暗示：如果這個 Dashboard 永遠沒有被建好，Phase 1 的工作也不會白費。反過來說，Phase 2 以後的工作能否帶來同等價值，取決於 Dashboard 是否真的會被使用。

### Insight 2：簡化的邊際效益遞減

從 Express + monorepo 到 Node 腳本 + Vite，這一步的簡化收益很大。但計畫已經在討論是否要砍掉 Chart.js（改用純 CSS）、是否要砍掉 TypeScript、是否要做純 HTML 報告——這些進一步的簡化，每一步的收益都在減少，但判斷的成本沒有減少。

每次說「不需要這個」，都需要花時間論證，而論證的時間可能比直接實作更長。計畫需要在某一點「停止簡化，開始實作」。

### Insight 3：這個工具的目標使用者是「未來的自己」，這個特殊性被忽視了

大多數軟體工具需要考慮多個使用者的不同需求。但這個 Dashboard 的使用者只有一個人，而且是建造者本人。這意味著：
- UI 不需要「直覺易用」，需要的是「建造者自己覺得有用」
- 功能的優先順序應該從「我現在最想知道什麼」出發，而不是從「四大功能全部做完」出發
- 如果某個功能建好了發現自己根本不用，可以直接砍掉，沒有任何代價

這個洞察暗示：與其設計一個「完整的四大功能 Dashboard」，不如先問「我今天最想看到的一個數字是什麼」，從那一個數字開始做。

### Insight 4：計畫文件本身正在示範 CLAUDE.md 的問題

task_plan.md 現在已經過時（Phase 2 的 checklist 和實際決策不符），但計畫沒有更新它。這正是 CLAUDE.md 自我迭代問題的縮影：文件很容易漂移成過時狀態，而且通常不會被察覺，因為真正的決策在腦袋裡，不在文件上。

這個 Dashboard 要解決的問題，在建 Dashboard 的過程中就已經在重現了。

## 七、具體改進建議

### 建議 1：先定義 data.json 的結構，再動手寫任何程式碼

具體做法：在 Phase 2 的第一個任務是手工寫一個 `data.json` 的範例，把每個欄位都定義清楚（名稱、型別、來源、用途）。這份文件就是腳本和前端的共同契約。

為什麼：沒有這份契約，腳本和前端開發會各自做假設，整合時才發現格式不對，需要返工。

### 建議 2：把「使用者要做什麼決策」寫進每個功能的定義

具體做法：每個 Dashboard 功能旁邊加一欄「使用者看到這個數字後，什麼情況下要採取什麼行動」。例如：Token 分析 → 「如果 CLAUDE.md 超過 8k tokens，考慮把某個區塊移到 docs/」。

為什麼：沒有行動指引的數據只是噪音。這也是讓 Dashboard 真正被使用而不是被遺忘的關鍵。

### 建議 3：立刻更新 task_plan.md 來反映第 1 輪的 20 點優化

具體做法：把 task_plan.md 中過時的條目（Express、monorepo、6 個階段）改為實際決定的架構，並把 20 點優化整合進來。保持計畫文件和實際決策的一致性是 Dashboard 這個工具的核心精神。

為什麼：計畫文件漂移這件事本身就是 CLAUDE.md 問題的縮影，從自身示範好習慣。

### 建議 4：Skills 管理 MVP 明確只做「已安裝列表 + 檔案大小」，不做使用頻率

具體做法：在功能定義中明確寫清楚：Skills 管理 v1 只顯示（1）已安裝哪些 skills、（2）每個 skill 的 markdown 字數、（3）skill 的描述摘要。使用頻率（需要 JSONL 解析）放到 v2。

為什麼：模糊的功能範圍是計畫最常見的陷阱。把邊界寫清楚，實作時不需要做決策，也不會在不知不覺中做了超出範圍的事情。

### 建議 5：加一個「資料新鮮度」顯示，解決矛盾 1 的使用者體驗問題

具體做法：data.json 裡加一個 `generatedAt` 欄位（ISO 時間戳），Dashboard 首頁顯示「資料最後更新：X 分鐘前」，並有一個「重新掃描」說明（告訴使用者跑 `npm run scan` 或 `npm run dashboard`）。

為什麼：使用者看到資料時需要知道這份資料是否是最新的，否則無法信任顯示的數字。

### 建議 6：全專案 CLAUDE.md 掃描要加明確的邊界定義

具體做法：在腳本中硬編碼或設定以下規則：（1）從 `~/Documents/`、`~/Developer/`、`~/Projects/`（或使用者指定的根目錄）開始掃；（2）跳過 `node_modules/`、`.git/`、Library、System；（3）深度限制 5 層。

為什麼：沒有邊界的檔案系統掃描在實際執行中可能掃到不相干的地方，或者跑太久。

### 建議 7：處理 auto-analyze 重複計數 bug 的去重邏輯，並在 Dashboard 中標注

具體做法：腳本在處理 auto-analyze 的輸出時，識別並去除重複的 session 計數（相同的 sessionId 只計一次）。在 Dashboard 的統計數字旁邊加一個小標注「已去除重複計數」。

為什麼：如果 Dashboard 顯示的數字和使用者直接看 auto-analyze 輸出看到的數字不一樣，使用者會困惑。透明化去重邏輯可以建立信任。

### 建議 8：驗證並清理 rules/ 目錄，作為 Phase 2 的第一個任務

具體做法：用 `/context` 指令確認 rules/ 的檔案是否仍在 Memory files 中被計入。如果是，評估是要清空 rules/ 還是移除這些舊檔案。這個動作本身就是 CLAUDE.md token 優化的一個行動項目，也可以作為 Dashboard「Token 分析→行動項目」的第一個實際案例。

為什麼：findings.md 記錄了這個問題但沒有後續行動。這個小任務可以驗證 Dashboard 的「行動指引」設計是否有效。

### 建議 9：最小可行版本重新定義——只做一個畫面，一個數字

具體做法：在 Phase 2 之前，先問「如果 Dashboard 只能顯示一件事，那件事是什麼」。從那個答案開始做，確保第一個可展示的版本能在一天內完成。

為什麼：計畫雖然已經簡化到「3 個階段」，但每個階段仍然很大。從最小可用單元出發，更符合「漸進式進步優於大爆炸」的開發哲學，也能最快得到使用者回饋���即使使用者就是開發者自己）。

## 總結

第 1 輪的核心貢獻是：把一個過度工程化的計畫（Express + monorepo + 全棧）拉回到合適的規模，並且通過 Phase 1 Discovery 驗證了三個關鍵假設（證明了 claude-log 的限制、auto-analyze 的 bug、以及變更追蹤方式）。

第 2 輪的核心任務應該是：補上 data.json 結構定義、明確每個功能的使用者行動指引、更新過時的 task_plan.md，然後從最小的可展示單元開始實作，快速獲得第一個真實的 Dashboard 畫面。

整體評分 7/10。技術判斷力強，但缺乏「完成後使用者能做什麼」的設計思考，以及計畫文件管理的一致性需要補強。
